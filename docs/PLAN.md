# Implementation Plan — Spades (Android/iOS)

## 1. Goal

A native-feeling Android + iOS Spades app with production-grade visual
polish — comparable to Netflix's NGP Hearts (smooth card animations,
tactile felt table, crisp vector card art, juicy micro-interactions) —
built from a single codebase.

## 2. Framework decision

| Option | Verdict |
|---|---|
| **Flutter (chosen)** | Skia/Impeller rendering gives pixel-perfect, GPU-accelerated vector graphics and 60fps animation with no native-per-platform work. One Dart codebase → iOS + Android (+ web/desktop later, free). Huge ecosystem for exactly this kind of UI (`AnimationController`, `Hero`, custom painters). Best fit for a card game's declarative, animation-heavy UI. |
| React Native (+ Skia/Reanimated) | Viable, but needs the separate `react-native-skia` dependency to get the same rendering quality Flutter has natively, and the JS bridge adds friction for tight physics-y card animations. |
| Unity / native engines | Overkill — built for 3D/heavy game loops; slower iteration for a UI-centric card game, larger app size, worse platform-native feel (text fields, settings, share sheets). |
| Fully native (Swift + Kotlin) | Best possible fidelity but 2x the implementation and maintenance cost; not justified for this scope. |

**Decision: Flutter (stable channel, Dart 3).** Reassess only if a
concrete Flutter limitation blocks a specific feature.

Key packages:
- `flutter_riverpod` — game/app state management (testable, no
  BuildContext coupling for the pure game engine).
- `flutter_animate` — declarative, chainable animation effects for
  card deals/flights/flips without hand-rolled `AnimationController`
  boilerplate everywhere.
- `google_fonts` — a clean numeral/label typeface for the HUD.
- No external card-art assets: card faces/backs are drawn with
  `CustomPainter` (crisp at any resolution, zero licensing risk,
  trivially themeable). A raster/Lottie asset pipeline can replace
  this later without touching game logic.
- `flutter_test` / `mocktail` for unit + widget tests.

## 3. Architecture

```
mobile/
  lib/
    core/                 # Pure Dart, zero Flutter imports. Unit-testable in isolation.
      models/             # Card, Suit, Rank, Player, Bid, Trick, Seat
      engine/             # Deck, dealing, bidding validation, trick resolution,
                           # scoring (bags/nil per docs/RULES.md), match/hand state machine
      ai/                 # Bot bidding heuristic + bot card-play heuristic
    state/                # Riverpod providers/notifiers wrapping core/engine for the UI
    ui/
      theme/              # Colors, felt gradients, text styles
      widgets/
        playing_card.dart # CustomPainter-based card face/back widget
        hand_fan.dart      # Arc-fanned hand layout + drag-to-play gesture
        trick_area.dart    # Center-table trick display + collection animation
        bid_sheet.dart     # Bidding bottom sheet
        scoreboard.dart
      screens/
        home_screen.dart
        new_game_screen.dart   # variant/target-score toggles from RULES.md §6-7
        table_screen.dart      # main gameplay screen
        round_summary_screen.dart
    app.dart
    main.dart
  test/                   # mirrors lib/core structure
  android/, ios/           # generated by `flutter create`, native shells
```

The `core/` package has **no Flutter dependency** so the entire rules
engine (deck, bidding, trick resolution, scoring, bots) is plain Dart
and runs under `dart test` with no widget/device needed — this is
where correctness bugs are cheapest to catch.

## 4. Visual design direction

"Quiet table, bright cards" — minimal, rich, elegant. The full design
language (palette, type, components, key screens) lives on the
"Spades Design Language" canvas; `mobile/lib/ui/theme/app_theme.dart`
holds the tokens.

- Palette: near-black felt `#0B1F19` with a whisper of vignette
  (`#13302A` raised), ivory cards `#F4EEE2`, text `#ECE4D2`, sage
  `#9DAA9F` for secondary text. Garnet `#A23B2E` and ink `#1C1B19` are
  the only pip colors; `#D98A7E` marks negative scores.
- One accent: brass `#C9A45C` only ever means "you can act now" — the
  "Your turn" pill, playable cards' ring, the bid you're about to
  place, the primary button. At most one solid brass element per screen.
- Type: Cormorant Garamond (600/700) for display, scores and card
  indices; Instrument Sans for UI; labels 11px, 600, +0.2em, caps.
- Cards: vector faces (no font glyphs) with a Cormorant rank index in
  the corners and one large center pip; backs are raised felt with a
  brass hairline and the spade monogram. Playable = lifted 14 + brass
  ring; not playable = 36% opacity; card winning the trick = brass ring.
- Motion: 180ms for lift/hover, 320ms card flight to the trick, 900ms
  hold on a completed trick before it clears; played cards settle at a
  small seat-specific tilt.
- Layout: human seat always at the bottom; North shows a small stack of
  card backs, West/East are seat tags only so nothing crowds the trick.
- Haptics + subtle sound cues on deal/play/trick-win (mobile only,
  toggleable) — not yet implemented.

## 5. Milestones

1. **Docs** (this file + `docs/RULES.md`) — done.
2. **Project scaffold** — `flutter create`, folder layout, lint config,
   CI-friendly `flutter analyze`/`flutter test` passing on an empty
   shell. *(this session)*
3. **Core engine** — models, deck/deal, bid validation, trick
   resolution, scoring incl. bags/nil, hand/match state machine, full
   unit test coverage. *(this session)*
4. **Bot AI v1** — rule-of-thumb bidding (count aces/spades/void suits)
   + greedy-legal trick play good enough to fill 3 seats convincingly.
5. **Table UI v1** — static felt table, seats, dealt hands, legal-move
   highlighting, tap-to-play, bidding sheet, scoreboard — playable
   end-to-end against bots without animation polish yet.
6. **Animation & juice pass** — dealing flight, card-play arcs, trick
   sweep, score pop-ins, sound/haptics.
7. **Settings & variants** — New Game screen wiring every toggle in
   `docs/RULES.md` §6-7 into the engine's `MatchConfig`.
8. **Platform packaging** — app icons/splash, Android signing config,
   iOS bundle metadata (iOS build itself requires Xcode on macOS —
   this Linux dev environment can build/verify Android and run all
   Dart analysis/tests, but a macOS machine or CI runner is needed to
   produce an actual .ipa).
9. **Polish/QA pass** — accessibility (color-blind suit markers),
   tablet layout, performance profiling.

This session focuses on milestones 2–3 (and a first pass at 4–5): a
scaffolded, analyzable, tested Flutter project with a working rules
engine, committed and pushed. Later sessions continue down the list.

## 6. Testing strategy

- `core/`: 100%-ish unit test coverage on scoring math (bags, nil,
  blind nil, set contracts) since these are the easiest place for a
  silent, high-impact bug.
- `state/`: notifier tests driving full hands via bots only.
- `ui/`: widget tests for critical interactions (only legal cards are
  tappable; bidding sheet validates 0–13).
- Manual: `flutter run` against an Android emulator/device for feel;
  this container can build/analyze but has no emulator/display, so
  final on-device verification happens in a follow-up session or by
  the user.
